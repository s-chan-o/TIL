# DB 설계와 쿼리 계획

## 정규화(Normalization)란 무엇이고 1NF~3NF

정규화는 **데이터 중복을 줄이고 데이터 정합성을 높이기 위해 테이블을 구조화하는 과정**이다.

하나의 테이블에 모든 데이터를 몰아넣으면 중복이 많아지고, 수정할 때 데이터 불일치가 발생할 수 있다.

```text
중복 데이터 증가 -> 수정/삭제/삽입 이상 발생 가능
```

정규화는 이런 문제를 줄이기 위해 테이블을 적절히 나누고 관계를 설정한다.

### 1NF(제1정규형)

1NF는 **하나의 컬럼에 하나의 값만 들어가야 한다는 규칙**이다.

나쁜 예시는 다음과 같다.

```text
user_id | name | phone
1       | Kim  | 010-1111, 010-2222
```

`phone` 컬럼에 여러 값이 들어가 있으므로 1NF를 만족하지 않는다.

1NF를 만족하려면 값을 원자적으로 나누어야 한다.

```text
user_id | name | phone
1       | Kim  | 010-1111
1       | Kim  | 010-2222
```

### 2NF(제2정규형)

2NF는 **1NF를 만족하면서, 기본키의 일부에만 의존하는 컬럼을 분리하는 규칙**이다.

주로 복합키를 사용할 때 문제가 된다.

```text
student_id | course_id | student_name | course_name
1          | 10        | Kim          | Database
```

여기서 `student_name`은 `student_id`에만 의존하고, `course_name`은 `course_id`에만 의존한다.  
복합키 전체에 의존하지 않으므로 테이블을 분리하는 것이 좋다.

### 3NF(제3정규형)

3NF는 **2NF를 만족하면서, 기본키가 아닌 컬럼이 다른 일반 컬럼에 의존하지 않도록 분리하는 규칙**이다.

```text
user_id | user_name | department_id | department_name
1       | Kim       | 10            | Backend
```

`department_name`은 `user_id`가 아니라 `department_id`에 의존한다.  
따라서 부서 정보를 별도 테이블로 분리하는 것이 좋다.

### 정리

- 정규화는 중복을 줄이고 데이터 정합성을 높이는 과정이다.
- 1NF는 컬럼 값을 원자적으로 만든다.
- 2NF는 기본키 일부에만 의존하는 컬럼을 분리한다.
- 3NF는 기본키가 아닌 컬럼에 의존하는 컬럼을 분리한다.

## JOIN의 종류와 차이

JOIN은 **두 개 이상의 테이블을 연결해서 조회하는 방법**이다.

관계형 DB에서는 데이터를 여러 테이블로 나누어 저장하기 때문에, 필요한 데이터를 함께 조회할 때 JOIN을 사용한다.

### INNER JOIN

INNER JOIN은 **두 테이블에서 조건이 일치하는 데이터만 조회**한다.

```text
A와 B에 모두 존재하는 데이터만 조회
```

```sql
SELECT *
FROM users u
INNER JOIN orders o ON u.id = o.user_id;
```

### LEFT JOIN

LEFT JOIN은 **왼쪽 테이블의 데이터는 모두 조회하고, 오른쪽 테이블은 조건이 맞는 데이터만 붙이는 방식**이다.

오른쪽 테이블에 매칭되는 데이터가 없으면 `NULL`로 나온다.

```sql
SELECT *
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;
```

### RIGHT JOIN

RIGHT JOIN은 **오른쪽 테이블의 데이터는 모두 조회하고, 왼쪽 테이블은 조건이 맞는 데이터만 붙이는 방식**이다.

```sql
SELECT *
FROM users u
RIGHT JOIN orders o ON u.id = o.user_id;
```

### FULL OUTER JOIN

FULL OUTER JOIN은 **양쪽 테이블의 데이터를 모두 조회하고, 매칭되지 않는 부분은 NULL로 채우는 방식**이다.

```text
A 전체 + B 전체
```

### CROSS JOIN

CROSS JOIN은 **두 테이블의 모든 조합을 만드는 방식**이다.

```text
A row 수 * B row 수
```

데이터가 많으면 결과가 매우 커질 수 있으므로 주의해야 한다.

### JOIN 비교

| JOIN 종류 | 설명 |
|---|---|
| INNER JOIN | 양쪽에 모두 매칭되는 데이터만 조회 |
| LEFT JOIN | 왼쪽 테이블은 모두 조회 |
| RIGHT JOIN | 오른쪽 테이블은 모두 조회 |
| FULL OUTER JOIN | 양쪽 테이블을 모두 조회 |
| CROSS JOIN | 모든 조합을 조회 |

### 정리

- 양쪽 모두 매칭되는 데이터만 필요하면 `INNER JOIN`을 사용한다.
- 기준 테이블의 데이터를 모두 유지하려면 `LEFT JOIN`을 많이 사용한다.
- 모든 조합이 필요할 때만 `CROSS JOIN`을 사용한다.

## 서브쿼리 vs JOIN 중 어떤 게 더 효율적인가

서브쿼리와 JOIN 중 항상 더 빠른 것은 없다.  
DB 옵티마이저, 데이터 양, 인덱스, 쿼리 구조에 따라 달라진다.

### 서브쿼리

서브쿼리는 **쿼리 안에 포함된 또 다른 쿼리**이다.

```sql
SELECT *
FROM users
WHERE id IN (
  SELECT user_id
  FROM orders
);
```

**특징**

- 쿼리 의도가 명확할 때가 있다.
- 단일 값이나 조건 필터링에 유용하다.
- 복잡하게 중첩되면 성능과 가독성이 떨어질 수 있다.

### JOIN

JOIN은 **테이블을 직접 연결해서 데이터를 조회하는 방식**이다.

```sql
SELECT u.*
FROM users u
JOIN orders o ON u.id = o.user_id;
```

**특징**

- 여러 테이블의 컬럼을 함께 조회하기 좋다.
- 인덱스를 잘 활용하면 성능이 좋다.
- 중복 row가 생길 수 있어 주의해야 한다.

### 효율 비교

일반적으로는 JOIN이 최적화에 유리한 경우가 많다.  
하지만 최신 DB는 서브쿼리를 JOIN으로 변환해서 실행하기도 하므로 무조건 JOIN이 빠르다고 말하면 안 된다.

중요한 것은 실제 실행계획을 확인하는 것이다.

```sql
EXPLAIN
SELECT ...
```

### 정리

- 서브쿼리와 JOIN 중 항상 더 빠른 것은 없다.
- 여러 테이블의 데이터를 함께 가져오면 JOIN이 유리한 경우가 많다.
- 단순 존재 여부나 조건 필터링은 서브쿼리가 더 읽기 쉬울 수 있다.
- 최종 판단은 실행계획과 실제 데이터 기준으로 해야 한다.

## N+1 문제란 무엇이고 어떻게 해결하나

N+1 문제는 **처음 쿼리 1번으로 N개의 데이터를 가져온 뒤, 각 데이터마다 추가 쿼리가 N번 더 실행되는 문제**이다.

예를 들어 게시글 10개를 조회한 뒤, 각 게시글의 작성자를 따로 조회하면 다음처럼 된다.

```text
게시글 목록 조회 1번
작성자 조회 10번
총 11번 쿼리 실행
```

데이터가 많아질수록 쿼리 수가 급격히 증가해 성능 문제가 발생한다.

### 발생 예시

```text
1. posts 조회
2. post[0].user 조회
3. post[1].user 조회
4. post[2].user 조회
...
```

ORM에서 지연 로딩을 사용할 때 자주 발생한다.

### 해결 방법

**JOIN FETCH**

연관된 데이터를 한 번에 가져온다.

```sql
SELECT p, u
FROM Post p
JOIN FETCH p.user u;
```

**일반 JOIN 사용**

필요한 테이블을 JOIN해서 한 번에 조회한다.

```sql
SELECT p.*, u.*
FROM posts p
JOIN users u ON p.user_id = u.id;
```

**Batch Size 설정**

연관 데이터를 하나씩 조회하지 않고 묶어서 조회한다.

```text
user_id IN (1, 2, 3, 4, 5)
```

**DTO 직접 조회**

필요한 데이터만 명확하게 조회한다.

```sql
SELECT p.title, u.name
FROM posts p
JOIN users u ON p.user_id = u.id;
```

### 정리

- N+1 문제는 1번의 조회 이후 N번의 추가 조회가 발생하는 문제이다.
- ORM의 지연 로딩에서 자주 발생한다.
- JOIN FETCH, JOIN, Batch Size, DTO 조회로 해결할 수 있다.
- 쿼리 로그와 실행 쿼리 수를 확인하는 것이 중요하다.

## 파티셔닝과 샤딩

### 파티셔닝(Partitioning)

파티셔닝은 **하나의 데이터베이스 안에서 큰 테이블을 여러 작은 단위로 나누는 방식**이다.

논리적으로는 하나의 테이블처럼 보이지만, 내부적으로는 여러 파티션으로 나뉘어 저장된다.

```text
orders 테이블
-> orders_2024
-> orders_2025
-> orders_2026
```

**특징**

- 같은 DB 안에서 테이블을 나눈다.
- 대용량 테이블 관리에 유리하다.
- 특정 범위만 조회하면 필요한 파티션만 읽을 수 있다.
- 주로 날짜, 범위, 해시 기준으로 나눈다.

### 샤딩(Sharding)

샤딩은 **데이터를 여러 데이터베이스 서버에 나누어 저장하는 방식**이다.

```text
user_id 1~1000   -> DB 1
user_id 1001~2000 -> DB 2
user_id 2001~3000 -> DB 3
```

**특징**

- 여러 DB 서버로 데이터를 분산한다.
- 수평 확장에 유리하다.
- 특정 서버에 부하가 몰리지 않게 할 수 있다.
- 분산 트랜잭션, 조인, 운영 복잡도가 증가한다.

### 파티셔닝과 샤딩 비교

| 구분 | 파티셔닝 | 샤딩 |
|---|---|---|
| 나누는 대상 | 하나의 DB 안의 테이블 | 여러 DB 서버 |
| 목적 | 큰 테이블 관리, 조회 최적화 | 수평 확장, 부하 분산 |
| 위치 | 같은 DB 내부 | 서로 다른 DB 서버 |
| 장점 | 관리와 범위 조회에 유리 | 대규모 트래픽 처리에 유리 |
| 단점 | 단일 DB 한계는 그대로 | 운영 복잡도 증가 |

### 정리

- 파티셔닝은 하나의 DB 안에서 큰 테이블을 나누는 방식이다.
- 샤딩은 여러 DB 서버에 데이터를 분산 저장하는 방식이다.
- 파티셔닝은 대용량 테이블 관리에 유리하다.
- 샤딩은 수평 확장과 트래픽 분산에 유리하다.
