# 심화 & 실무

## DB 복제(Replication)란 무엇이고 왜 사용하나

DB 복제는 **하나의 데이터베이스 데이터를 다른 DB 서버에 복사해서 유지하는 방식**이다.

보통 원본 DB를 `Primary` 또는 `Master`, 복제 DB를 `Replica` 또는 `Slave`라고 부른다.

```text
Primary DB -> Replica DB
```

### 사용하는 이유

- 장애 발생 시 복제 DB로 전환할 수 있다.
- 읽기 요청을 Replica로 분산해 부하를 줄일 수 있다.
- 백업이나 분석 작업을 Replica에서 처리할 수 있다.
- 데이터 안정성과 가용성을 높일 수 있다.

### 주의할 점

복제는 보통 약간의 지연이 발생할 수 있다.  
Primary에 쓴 데이터가 Replica에 바로 반영되지 않을 수 있는데, 이를 **복제 지연(Replication Lag)** 이라고 한다.

```text
쓰기: Primary
읽기: Replica
-> 방금 쓴 데이터가 안 보일 수 있음
```

### 정리

- Replication은 데이터를 다른 DB 서버에 복사하는 방식이다.
- 장애 대응, 읽기 부하 분산, 백업 목적으로 사용한다.
- 복제 지연 때문에 읽기 정합성 문제가 생길 수 있다.

## Redis를 캐시로 사용할 때 캐시 전략

Redis는 메모리 기반 저장소라서 DB보다 빠르게 데이터를 읽을 수 있다.  
자주 조회되는 데이터를 Redis에 저장해 DB 부하를 줄이는 데 많이 사용한다.

### Cache Aside

Cache Aside는 **애플리케이션이 캐시를 먼저 확인하고, 없으면 DB에서 조회한 뒤 캐시에 저장하는 방식**이다.

```text
1. Redis 조회
2. 캐시에 없으면 DB 조회
3. DB 결과를 Redis에 저장
4. 응답 반환
```

가장 많이 사용하는 방식이다.

**장점**

- 구현이 단순하다.
- 필요한 데이터만 캐싱할 수 있다.

**단점**

- 캐시 미스 시 DB 조회가 발생한다.
- 캐시와 DB 데이터가 일시적으로 다를 수 있다.

### Write Through

Write Through는 **데이터를 쓸 때 DB와 캐시에 동시에 반영하는 방식**이다.

```text
쓰기 요청 -> DB 저장 + Redis 저장
```

**장점**

- 캐시와 DB의 정합성을 비교적 유지하기 쉽다.

**단점**

- 쓰기 성능이 느려질 수 있다.
- 자주 읽지 않는 데이터까지 캐시에 저장될 수 있다.

### Write Back

Write Back은 **먼저 캐시에 쓰고, 나중에 DB에 반영하는 방식**이다.

```text
쓰기 요청 -> Redis 저장 -> 나중에 DB 반영
```

**장점**

- 쓰기 성능이 빠르다.

**단점**

- 캐시 장애 시 데이터 유실 위험이 있다.
- 구현과 운영 난이도가 높다.

### TTL 설정

캐시는 오래된 데이터가 계속 남지 않도록 만료 시간을 설정하는 것이 중요하다.

```text
TTL: 캐시 데이터의 생존 시간
```

TTL이 너무 짧으면 캐시 효과가 떨어지고, 너무 길면 오래된 데이터를 보여줄 수 있다.

### 정리

- Redis 캐시는 DB 부하를 줄이고 응답 속도를 높이기 위해 사용한다.
- 가장 흔한 방식은 Cache Aside이다.
- 데이터 정합성이 중요하면 TTL, 삭제, 갱신 전략을 함께 고려해야 한다.

## 인덱스를 잘못 사용하면 오히려 느려지는 이유

인덱스는 조회를 빠르게 하지만, 항상 좋은 것은 아니다.  
잘못 사용하면 오히려 성능이 떨어질 수 있다.

### 쓰기 성능 저하

인덱스가 많으면 `INSERT`, `UPDATE`, `DELETE` 시 테이블뿐 아니라 인덱스도 함께 갱신해야 한다.

```text
데이터 변경 -> 테이블 변경 + 인덱스 변경
```

그래서 인덱스가 많을수록 쓰기 성능이 떨어질 수 있다.

### 선택도가 낮은 컬럼

값의 종류가 적은 컬럼은 인덱스 효율이 낮다.

예를 들어 `gender`, `status`처럼 값 종류가 적은 컬럼은 많은 row가 같은 값을 가진다.

```text
status = ACTIVE
-> 전체 데이터의 대부분이 ACTIVE라면 인덱스 효율 낮음
```

이 경우 인덱스를 타도 많은 데이터를 읽어야 하므로 효과가 작다.

### 함수나 연산 사용

조건절에서 인덱스 컬럼에 함수나 연산을 적용하면 인덱스를 제대로 사용하지 못할 수 있다.

```sql
WHERE YEAR(created_at) = 2026
```

대신 범위 조건으로 작성하는 것이 좋다.

```sql
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01'
```

### 너무 많은 인덱스

인덱스가 많으면 저장 공간이 늘어나고, DB 옵티마이저가 잘못된 인덱스를 선택할 가능성도 생긴다.

### 정리

- 인덱스는 조회를 빠르게 하지만 쓰기 비용을 증가시킨다.
- 선택도가 낮은 컬럼은 인덱스 효율이 낮을 수 있다.
- 컬럼에 함수나 연산을 걸면 인덱스를 못 탈 수 있다.
- 인덱스는 많이 만드는 것이 아니라 필요한 쿼리에 맞게 설계해야 한다.

## DB 커넥션 풀(Connection Pool)이란 무엇인가

DB 커넥션 풀은 **DB 연결을 미리 여러 개 만들어두고 재사용하는 방식**이다.

애플리케이션이 요청마다 DB 연결을 새로 만들면 비용이 크다.

```text
요청마다 연결 생성 -> 인증 -> 쿼리 실행 -> 연결 종료
```

커넥션 풀은 연결을 미리 만들어두고 필요한 요청에 빌려준다.

```text
요청 -> 풀에서 커넥션 대여 -> 쿼리 실행 -> 풀에 반환
```

### 장점

- DB 연결 생성 비용을 줄일 수 있다.
- 요청 처리 속도를 높일 수 있다.
- 동시에 사용할 DB 연결 수를 제한할 수 있다.
- DB에 과도한 연결이 몰리는 것을 막을 수 있다.

### 주의할 점

커넥션 풀 크기가 너무 작으면 요청이 커넥션을 기다리게 된다.  
반대로 너무 크면 DB에 과도한 부하를 줄 수 있다.

```text
풀 크기 작음 -> 대기 증가
풀 크기 큼 -> DB 부하 증가
```

### 정리

- 커넥션 풀은 DB 연결을 미리 만들어두고 재사용하는 방식이다.
- 연결 생성 비용을 줄이고 성능을 높인다.
- 풀 크기는 애플리케이션 트래픽과 DB 처리 능력에 맞게 설정해야 한다.

## 트랜잭션 전파(Transaction Propagation)란 무엇인가

트랜잭션 전파는 **이미 트랜잭션이 있는 상태에서 다른 트랜잭션 메서드를 호출할 때 어떻게 처리할지 정하는 규칙**이다.

Spring에서는 `@Transactional`의 `propagation` 옵션으로 설정한다.

```java
@Transactional(propagation = Propagation.REQUIRED)
public void method() {
}
```

### REQUIRED

`REQUIRED`는 기본값이다.  
기존 트랜잭션이 있으면 참여하고, 없으면 새로 만든다.

```text
기존 트랜잭션 있음 -> 참여
기존 트랜잭션 없음 -> 새로 생성
```

### REQUIRES_NEW

`REQUIRES_NEW`는 항상 새로운 트랜잭션을 만든다.  
기존 트랜잭션이 있으면 잠시 중단하고 새 트랜잭션을 실행한다.

```text
기존 트랜잭션 중단 -> 새 트랜잭션 실행
```

로그 저장, 이력 저장처럼 메인 트랜잭션과 별도로 커밋해야 할 때 사용할 수 있다.

### SUPPORTS

`SUPPORTS`는 기존 트랜잭션이 있으면 참여하고, 없으면 트랜잭션 없이 실행한다.

### MANDATORY

`MANDATORY`는 반드시 기존 트랜잭션이 있어야 한다.  
없으면 예외가 발생한다.

### NOT_SUPPORTED

`NOT_SUPPORTED`는 트랜잭션 없이 실행한다.  
기존 트랜잭션이 있으면 중단한다.

### NEVER

`NEVER`는 트랜잭션이 있으면 예외가 발생한다.

### NESTED

`NESTED`는 기존 트랜잭션 안에서 중첩 트랜잭션을 만든다.  
일부 작업만 롤백하고 전체 트랜잭션은 유지할 때 사용할 수 있다.

### 정리

- 트랜잭션 전파는 트랜잭션이 중첩 호출될 때의 동작 규칙이다.
- Spring 기본값은 `REQUIRED`이다.
- `REQUIRES_NEW`는 기존 트랜잭션과 분리된 새 트랜잭션을 만든다.
- 전파 옵션을 잘못 사용하면 의도치 않은 커밋이나 롤백이 발생할 수 있다.

## CAP 정리(CAP Theorem)

CAP 정리는 **분산 시스템에서 Consistency, Availability, Partition Tolerance 세 가지를 동시에 완벽하게 만족할 수 없다는 이론**이다.

### C: Consistency

일관성은 **모든 노드가 같은 시점에 같은 데이터를 보여주는 것**이다.

```text
어느 서버에 요청해도 같은 결과를 반환
```

### A: Availability

가용성은 **모든 요청에 대해 항상 응답을 반환하는 것**이다.

```text
일부 노드에 문제가 있어도 응답은 해야 함
```

### P: Partition Tolerance

분할 허용성은 **네트워크 장애로 노드 간 통신이 끊겨도 시스템이 동작하는 것**이다.

분산 시스템에서는 네트워크 장애를 피할 수 없기 때문에 보통 P는 반드시 고려해야 한다.

### CP와 AP

네트워크 분할이 발생했을 때 선택은 보통 CP 또는 AP로 나뉜다.

**CP 시스템**

일관성을 우선한다.  
일부 요청을 실패시키더라도 데이터 정합성을 지킨다.

```text
정합성 우선, 가용성 일부 희생
```

**AP 시스템**

가용성을 우선한다.  
일단 응답을 제공하고, 나중에 데이터가 맞춰질 수 있다.

```text
가용성 우선, 일관성 일부 희생
```

### 정리

- CAP는 일관성, 가용성, 분할 허용성을 의미한다.
- 분산 시스템에서 세 가지를 동시에 완벽하게 만족할 수 없다.
- 네트워크 분할 상황에서는 보통 일관성과 가용성 중 하나를 선택해야 한다.
- 정합성이 중요하면 CP, 항상 응답이 중요하면 AP 성향을 선택한다.
