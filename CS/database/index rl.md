# 인덱스 관련

## 인덱스란 무엇이고 어떻게 동작하나

인덱스는 **데이터베이스에서 원하는 데이터를 빠르게 찾기 위해 사용하는 자료구조**이다.

책의 목차나 색인처럼, 전체 데이터를 처음부터 끝까지 확인하지 않고 필요한 데이터의 위치를 빠르게 찾게 해준다.

```text
인덱스 없음: 테이블 전체를 순서대로 확인
인덱스 있음: 인덱스를 통해 필요한 위치를 빠르게 찾음
```

### 동작 원리

데이터베이스는 특정 컬럼에 인덱스를 만들면, 해당 컬럼 값을 기준으로 정렬된 자료구조를 따로 만든다.

예를 들어 `users.email` 컬럼에 인덱스를 만들면 다음과 같은 구조가 생긴다.

```text
email 값 -> 실제 데이터 위치
```

조회할 때는 테이블 전체를 직접 탐색하지 않고, 먼저 인덱스에서 조건에 맞는 값을 찾은 뒤 실제 row에 접근한다.

```sql
SELECT *
FROM users
WHERE email = 'test@example.com';
```

위 쿼리에서 `email`에 인덱스가 있다면, DB는 인덱스를 이용해 해당 email의 위치를 빠르게 찾는다.

### 인덱스가 빠른 이유

인덱스는 보통 B-Tree 또는 B+Tree 같은 균형 트리 구조로 관리된다.

트리 구조에서는 탐색 범위를 단계적으로 줄일 수 있어 전체 데이터를 모두 확인하지 않아도 된다.

```text
전체 탐색: O(n)
인덱스 탐색: O(log n)
```

### 장점

- 조회 속도를 빠르게 할 수 있다.
- `WHERE`, `ORDER BY`, `JOIN` 성능 개선에 도움이 된다.
- 범위 검색에도 유리하다.

### 단점

- 인덱스를 저장하기 위한 추가 공간이 필요하다.
- `INSERT`, `UPDATE`, `DELETE` 시 인덱스도 함께 갱신해야 한다.
- 인덱스가 너무 많으면 쓰기 성능이 떨어질 수 있다.

### 주의할 점

- 조회가 자주 일어나는 컬럼에 인덱스를 거는 것이 좋다.
- 값의 종류가 너무 적은 컬럼은 인덱스 효율이 낮을 수 있다.
- 인덱스를 많이 만든다고 무조건 좋은 것은 아니다.
- 조건절에서 인덱스 컬럼을 함수로 감싸면 인덱스를 제대로 못 탈 수 있다.

```sql
WHERE YEAR(created_at) = 2026 -- 인덱스 사용이 어려울 수 있음
```

대신 범위 조건으로 작성하는 것이 좋다.

```sql
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01'
```

### 정리

- 인덱스는 데이터를 빠르게 찾기 위한 자료구조이다.
- 전체 테이블을 탐색하지 않고 인덱스를 통해 필요한 위치를 찾는다.
- 조회 성능은 좋아지지만 쓰기 성능과 저장 공간 비용이 증가한다.
- 자주 조회되는 컬럼에 신중하게 적용해야 한다.

## 클러스터드 인덱스와 논클러스터드 인덱스의 차이

### 클러스터드 인덱스(Clustered Index)

클러스터드 인덱스는 **인덱스 순서와 실제 데이터 저장 순서가 같은 인덱스**이다.

즉, 테이블의 row 자체가 인덱스 기준으로 정렬되어 저장된다.

```text
인덱스 순서 = 실제 데이터 저장 순서
```

예를 들어 `id`를 기준으로 클러스터드 인덱스를 만들면 데이터가 `id` 순서대로 저장된다.

```text
id: 1 -> 2 -> 3 -> 4
```

**특징**

- 실제 데이터가 인덱스 순서대로 정렬된다.
- 테이블당 보통 하나만 만들 수 있다.
- 범위 조회에 유리하다.
- 기본키를 만들면 클러스터드 인덱스로 생성되는 DB가 많다.

### 논클러스터드 인덱스(Non-Clustered Index)

논클러스터드 인덱스는 **인덱스와 실제 데이터 저장 순서가 다른 인덱스**이다.

인덱스는 별도의 구조로 저장되고, 인덱스에는 실제 데이터 위치를 가리키는 정보가 들어 있다.

```text
인덱스 -> 실제 데이터 위치
```

예를 들어 `email`에 논클러스터드 인덱스를 만들면, email 값은 인덱스에서 정렬되어 있고 실제 row 위치를 가리킨다.

```text
email index -> row 위치
```

**특징**

- 실제 데이터의 저장 순서를 바꾸지 않는다.
- 한 테이블에 여러 개 만들 수 있다.
- 특정 컬럼으로 빠르게 조회할 때 유리하다.
- 인덱스 탐색 후 실제 데이터에 한 번 더 접근할 수 있다.

### 비교

| 구분 | 클러스터드 인덱스 | 논클러스터드 인덱스 |
|---|---|---|
| 데이터 저장 순서 | 인덱스 순서와 같음 | 인덱스 순서와 다름 |
| 실제 데이터 위치 | leaf node에 실제 데이터 저장 | leaf node에 데이터 위치 저장 |
| 개수 | 테이블당 보통 1개 | 여러 개 가능 |
| 장점 | 범위 조회에 유리 | 다양한 조건 조회에 유리 |
| 단점 | 데이터 삽입/수정 시 정렬 유지 비용 발생 | 인덱스 탐색 후 실제 데이터 접근 비용 발생 |

### 정리

- 클러스터드 인덱스는 실제 데이터를 인덱스 순서대로 정렬한다.
- 논클러스터드 인덱스는 별도 인덱스 구조에서 실제 데이터 위치를 가리킨다.
- 클러스터드 인덱스는 테이블당 보통 하나만 가능하다.
- 논클러스터드 인덱스는 여러 개 만들 수 있다.
- 범위 조회는 클러스터드 인덱스가 유리하고, 다양한 검색 조건은 논클러스터드 인덱스가 유리하다.

## 복합 인덱스란 무엇이고 컬럼 순서가 중요한 이유

복합 인덱스는 **두 개 이상의 컬럼을 함께 묶어서 만든 인덱스**이다.

```sql
CREATE INDEX idx_user_name_age
ON users (name, age);
```

위 인덱스는 `name`과 `age`를 함께 기준으로 정렬된 인덱스이다.

```text
(name, age) 순서로 정렬됨
```

### 컬럼 순서가 중요한 이유

복합 인덱스는 앞에 있는 컬럼부터 순서대로 사용된다.  
이를 **왼쪽 접두사 원칙(Leftmost Prefix Rule)** 이라고 한다.

예를 들어 `(name, age)` 순서로 복합 인덱스를 만들었다면 다음 조건에서는 인덱스를 잘 사용할 수 있다.

```sql
WHERE name = 'Kim';

WHERE name = 'Kim'
  AND age = 18;
```

하지만 앞 컬럼인 `name` 없이 뒤 컬럼인 `age`만 조건으로 사용하면 인덱스를 제대로 활용하기 어렵다.

```sql
WHERE age = 18;
```

즉, `(name, age)` 인덱스는 `name` 기준으로 먼저 정렬되어 있기 때문에 `age`만으로는 효율적으로 찾기 어렵다.

### 범위 조건 주의

복합 인덱스에서 앞 컬럼에 범위 조건이 걸리면, 그 뒤 컬럼은 인덱스 활용도가 떨어질 수 있다.

```sql
WHERE name > 'Kim'
  AND age = 18;
```

위 경우 `name`은 범위 조건으로 사용되지만, 그 뒤의 `age` 조건은 인덱스에서 효율적으로 사용되지 않을 수 있다.

### 컬럼 순서 정하는 기준

복합 인덱스의 컬럼 순서는 쿼리 패턴을 기준으로 정해야 한다.

- 자주 조건에 사용되는 컬럼을 앞에 둔다.
- 동등 조건(`=`)으로 자주 조회하는 컬럼을 앞에 둔다.
- 범위 조건(`<`, `>`, `BETWEEN`) 컬럼은 보통 뒤쪽에 둔다.
- 정렬(`ORDER BY`)과 함께 쓰이는 컬럼 순서도 고려한다.

### 정리

- 복합 인덱스는 여러 컬럼을 묶어 만든 인덱스이다.
- 복합 인덱스는 앞 컬럼부터 순서대로 사용된다.
- `(name, age)` 인덱스는 `name`, `name + age` 조건에 유리하다.
- `age`만 조건으로 사용하면 인덱스 효율이 낮다.
- 컬럼 순서는 실제 자주 실행되는 쿼리 조건을 기준으로 정해야 한다.

## 실행계획이란 무엇이고 어떻게 활용하나

실행계획은 **DB가 SQL을 어떤 방식으로 실행할지 보여주는 계획표**이다.

SQL을 실행하면 DB는 여러 실행 방법 중 비용이 가장 낮다고 판단한 방법을 선택한다.  
실행계획을 보면 쿼리가 인덱스를 사용하는지, 테이블 전체를 스캔하는지, 조인을 어떤 방식으로 처리하는지 확인할 수 있다.

```sql
EXPLAIN
SELECT *
FROM users
WHERE email = 'test@example.com';
```

### 실행계획을 보는 이유

실행계획은 쿼리 성능 문제를 분석할 때 사용한다.

- 인덱스를 제대로 사용하는지 확인한다.
- 불필요한 Full Scan이 발생하는지 확인한다.
- 조인 순서와 조인 방식을 확인한다.
- 예상 row 수가 너무 큰지 확인한다.
- 정렬이나 임시 테이블 사용 여부를 확인한다.

### 주요 확인 항목

| 항목 | 의미 |
|---|---|
| access type | 데이터를 찾는 방식 |
| key | 실제 사용된 인덱스 |
| rows | DB가 읽을 것으로 예상한 row 수 |
| Extra | 추가 작업 정보 |

### 자주 보는 신호

**좋은 신호**

- 적절한 인덱스를 사용한다.
- 읽는 row 수가 적다.
- 불필요한 정렬이나 임시 테이블이 없다.

**주의해야 할 신호**

- 테이블 전체를 스캔한다.
- 예상 rows 수가 너무 크다.
- 인덱스를 만들었는데 사용하지 않는다.
- 정렬이나 임시 테이블이 많이 발생한다.

### 활용 방법

실행계획을 보고 다음과 같이 쿼리를 개선할 수 있다.

- 자주 조회되는 조건 컬럼에 인덱스를 추가한다.
- 사용되지 않는 인덱스를 제거한다.
- 복합 인덱스의 컬럼 순서를 조정한다.
- 조건절에서 인덱스 컬럼을 함수로 감싸지 않도록 수정한다.
- 너무 많은 데이터를 읽는 쿼리는 조건을 더 구체화한다.

### 정리

- 실행계획은 DB가 SQL을 어떻게 실행할지 보여주는 정보이다.
- 쿼리가 인덱스를 타는지 확인할 때 사용한다.
- Full Scan, 과도한 rows, 불필요한 정렬이 있는지 확인해야 한다.
- 실행계획을 기반으로 인덱스 설계와 쿼리 구조를 개선할 수 있다.
