
# 트랜잭션 관련

## 트랜잭션(Transaction)이란 무엇이고 ACID 특성

트랜잭션은 **데이터베이스에서 하나의 작업 단위로 처리되어야 하는 연산들의 묶음**이다.

예를 들어 계좌 이체는 다음 두 작업이 모두 성공해야 한다.

```text
1. A 계좌에서 돈 차감
2. B 계좌에 돈 추가
```

둘 중 하나만 성공하면 데이터가 이상해지므로, 두 작업은 하나의 트랜잭션으로 묶어 처리해야 한다.

### ACID

트랜잭션은 ACID 특성을 가져야 한다.

| 특성 | 의미 |
|---|---|
| Atomicity | 원자성 |
| Consistency | 일관성 |
| Isolation | 격리성 |
| Durability | 지속성 |

### 원자성(Atomicity)

원자성은 **트랜잭션의 작업이 모두 성공하거나 모두 실패해야 한다는 특성**이다.

```text
모두 성공 -> COMMIT
하나라도 실패 -> ROLLBACK
```

### 일관성(Consistency)

일관성은 **트랜잭션 수행 전후에 데이터베이스의 규칙과 제약조건이 유지되어야 한다는 특성**이다.

예를 들어 잔액이 음수가 될 수 없다는 규칙이 있다면, 트랜잭션 이후에도 이 규칙이 깨지면 안 된다.

### 격리성(Isolation)

격리성은 **동시에 실행되는 트랜잭션들이 서로 영향을 주지 않도록 보장하는 특성**이다.

여러 트랜잭션이 동시에 실행되어도, 각각 독립적으로 실행되는 것처럼 보여야 한다.

### 지속성(Durability)

지속성은 **트랜잭션이 성공적으로 완료되면 그 결과가 영구적으로 저장되어야 한다는 특성**이다.

커밋 이후에는 DB 장애가 발생해도 데이터가 보존되어야 한다.

### 정리

- 트랜잭션은 하나의 논리적 작업 단위이다.
- 성공하면 `COMMIT`, 실패하면 `ROLLBACK`한다.
- ACID는 원자성, 일관성, 격리성, 지속성을 의미한다.

## 트랜잭션 격리 수준(Isolation Level) 4가지

트랜잭션 격리 수준은 **동시에 실행되는 트랜잭션들이 서로의 변경 내용을 어느 정도까지 볼 수 있는지 정하는 기준**이다.

격리 수준이 높을수록 데이터 정합성은 좋아지지만, 동시성은 낮아질 수 있다.

### Read Uncommitted

`Read Uncommitted`는 **커밋되지 않은 데이터도 읽을 수 있는 가장 낮은 격리 수준**이다.

다른 트랜잭션이 아직 커밋하지 않은 변경 내용을 읽을 수 있기 때문에 `Dirty Read`가 발생할 수 있다.

```text
트랜잭션 A가 아직 커밋하지 않은 값
-> 트랜잭션 B가 읽을 수 있음
```

### Read Committed

`Read Committed`는 **커밋된 데이터만 읽을 수 있는 격리 수준**이다.

`Dirty Read`는 막을 수 있지만, 같은 트랜잭션 안에서 같은 데이터를 다시 읽었을 때 값이 달라지는 `Non-Repeatable Read`가 발생할 수 있다.

### Repeatable Read

`Repeatable Read`는 **트랜잭션 안에서 같은 데이터를 여러 번 읽어도 같은 결과를 보장하는 격리 수준**이다.

`Dirty Read`와 `Non-Repeatable Read`를 막을 수 있다.  
하지만 DB에 따라 새로운 row가 추가되어 보이는 `Phantom Read`가 발생할 수 있다.

### Serializable

`Serializable`은 **트랜잭션을 순차적으로 실행한 것처럼 보장하는 가장 높은 격리 수준**이다.

정합성은 가장 강하지만, 동시성이 낮아지고 성능 비용이 커질 수 있다.

### 격리 수준 비교

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 특징 |
|---|---|---|---|---|
| Read Uncommitted | 발생 가능 | 발생 가능 | 발생 가능 | 가장 낮은 격리 수준 |
| Read Committed | 방지 | 발생 가능 | 발생 가능 | 커밋된 데이터만 읽음 |
| Repeatable Read | 방지 | 방지 | 발생 가능 | 같은 row 재조회 결과 보장 |
| Serializable | 방지 | 방지 | 방지 | 가장 강한 격리 수준 |

### 정리

- 격리 수준은 정합성과 동시성의 균형을 조절한다.
- 격리 수준이 높을수록 안전하지만 성능 비용이 커질 수 있다.
- 일반적으로 `Read Committed`나 `Repeatable Read`를 많이 사용한다.

## 교착 상태(Deadlock)란 무엇이고 어떻게 해결하나

교착 상태는 **두 개 이상의 트랜잭션이 서로가 가진 락을 기다리며 무한 대기하는 상태**이다.

예를 들어 다음 상황에서 교착 상태가 발생할 수 있다.

```text
트랜잭션 A: user row 락 획득 -> order row 락 대기
트랜잭션 B: order row 락 획득 -> user row 락 대기
```

A는 B가 가진 락을 기다리고, B는 A가 가진 락을 기다리기 때문에 서로 진행할 수 없다.

### 발생 원인

- 여러 트랜잭션이 서로 다른 순서로 자원에 접근한다.
- 트랜잭션이 너무 오래 락을 잡고 있다.
- 한 트랜잭션 안에서 너무 많은 데이터를 수정한다.

### 해결 방법

DB는 보통 교착 상태를 감지하면 하나의 트랜잭션을 강제로 롤백시킨다.

애플리케이션에서는 다음과 같이 대응할 수 있다.

- 트랜잭션을 짧게 유지한다.
- 여러 자원에 접근할 때 항상 같은 순서로 접근한다.
- 필요한 데이터만 잠근다.
- 인덱스를 적절히 사용해 잠금 범위를 줄인다.
- 교착 상태 발생 시 재시도 로직을 둔다.

### 정리

- 교착 상태는 서로의 락을 기다리며 트랜잭션이 멈추는 상태이다.
- 접근 순서가 다르거나 락을 오래 잡을 때 발생하기 쉽다.
- 트랜잭션을 짧게 유지하고, 자원 접근 순서를 통일하는 것이 중요하다.
- 발생 시 롤백 후 재시도하는 방식으로 처리할 수 있다.

## 낙관적 락과 비관적 락

동시에 같은 데이터를 수정하면 데이터 충돌이 발생할 수 있다.  
이를 제어하기 위해 낙관적 락과 비관적 락을 사용한다.

### 낙관적 락(Optimistic Lock)

낙관적 락은 **충돌이 자주 발생하지 않을 것이라고 보고, 먼저 락을 걸지 않고 수정 시점에 충돌을 검사하는 방식**이다.

보통 `version` 컬럼을 사용한다.

```text
1. 데이터를 조회할 때 version도 함께 읽는다.
2. 수정할 때 기존 version과 현재 version이 같은지 확인한다.
3. 같으면 수정하고 version을 증가시킨다.
4. 다르면 다른 트랜잭션이 먼저 수정한 것이므로 실패 처리한다.
```

**특징**

- 실제 DB 락을 오래 잡지 않는다.
- 동시성이 좋다.
- 충돌이 적은 환경에 적합하다.
- 충돌 발생 시 재시도나 예외 처리가 필요하다.

### 비관적 락(Pessimistic Lock)

비관적 락은 **충돌이 발생할 것이라고 보고, 데이터를 읽거나 수정할 때 미리 락을 거는 방식**이다.

다른 트랜잭션은 해당 락이 풀릴 때까지 기다려야 한다.

```sql
SELECT *
FROM users
WHERE id = 1
FOR UPDATE;
```

**특징**

- 충돌을 확실하게 막을 수 있다.
- 락을 잡는 동안 다른 트랜잭션이 대기한다.
- 동시성이 낮아질 수 있다.
- 교착 상태가 발생할 수 있다.

### 비교

| 구분 | 낙관적 락 | 비관적 락 |
|---|---|---|
| 관점 | 충돌이 적을 것이라 가정 | 충돌이 많을 것이라 가정 |
| 방식 | 수정 시점에 version 확인 | 미리 DB 락 획득 |
| 장점 | 동시성 좋음 | 충돌 방지 강함 |
| 단점 | 충돌 시 재시도 필요 | 대기, 교착 상태 가능 |
| 적합한 경우 | 충돌이 적은 환경 | 충돌이 잦거나 정합성이 매우 중요한 환경 |

### 정리

- 낙관적 락은 먼저 락을 걸지 않고 수정 시점에 충돌을 확인한다.
- 비관적 락은 먼저 락을 걸어 다른 트랜잭션의 접근을 막는다.
- 충돌이 적으면 낙관적 락, 충돌이 많고 정합성이 중요하면 비관적 락이 적합하다.

## MVCC(Multi-Version Concurrency Control)란 무엇인가

MVCC는 **하나의 데이터를 여러 버전으로 관리해서 읽기와 쓰기의 충돌을 줄이는 동시성 제어 방식**이다.

일반적으로 읽기 작업과 쓰기 작업이 동시에 일어나면 서로 락을 기다릴 수 있다.  
MVCC는 데이터의 이전 버전을 보관해두고, 읽기 트랜잭션이 적절한 버전의 데이터를 읽게 한다.

```text
현재 데이터: version 3
이전 데이터: version 1, version 2
```

### 동작 방식

```text
1. 트랜잭션이 데이터를 수정하면 기존 데이터를 바로 덮어쓰지 않는다.
2. 새로운 버전의 데이터를 만든다.
3. 읽기 트랜잭션은 자신의 시점에 맞는 버전을 읽는다.
4. 오래된 버전은 더 이상 필요 없을 때 정리된다.
```

예를 들어 트랜잭션 A가 데이터를 읽는 동안 트랜잭션 B가 같은 데이터를 수정해도, A는 자신이 시작한 시점의 데이터 버전을 계속 읽을 수 있다.

### 장점

- 읽기 작업이 쓰기 작업을 막지 않는다.
- 쓰기 작업이 읽기 작업을 막지 않는다.
- 동시성이 좋아진다.
- 일관된 읽기 결과를 제공할 수 있다.

### 단점

- 여러 버전을 관리해야 하므로 저장 공간이 더 필요하다.
- 오래된 버전을 정리하는 비용이 있다.
- 트랜잭션이 오래 유지되면 오래된 버전이 계속 남을 수 있다.

### 정리

- MVCC는 데이터를 여러 버전으로 관리하는 동시성 제어 방식이다.
- 읽기와 쓰기의 충돌을 줄여 동시성을 높인다.
- 읽기 트랜잭션은 자신에게 맞는 시점의 데이터 버전을 읽는다.
- PostgreSQL, MySQL InnoDB 등에서 사용된다.
