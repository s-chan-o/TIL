# 인프라, 실무 관련

## 로드밸런서

로드밸런서는 여러 서버에 트래픽을 분산시켜 단일 서버 과부하를 방지하고 고가용성을 제공한다.

**L4 로드밸런서**

- TCP/UDP 레벨에서 IP + 포트 정보만 보고 라우팅
- 내용을 볼 수 없어 단순하지만 매우 빠름

**L7 로드밸런서**

- HTTP 헤더, URL, 쿠키, 바디까지만 보고 라우팅 결정
- URL 경로 기반 라우팅
- 인증, 압축 SSL 종료 캐싱 기능

## 프록시, 리버스 프록시

**포워드 프록시**

클라이언트 앞에 위치해 클라이언트 대신 외부에 요청을 보낸다.
서버 입장에서는 실제 클라이언트 IP를 모른다.

- 용도 : 익명성, 호시ㅏ 내부망 인터넷 접속 제어, 콘텐츠 필터링, 캐싱

**리버스 프록시**

서버 앞에 위치해 클라이언트 요청을 받아 내부 서버로 전달한다. 클라이언트 입장에서는 실제 서버 주소를 모른다.

- 용도 : 로드밸런싱, SSL 종료, 캐싱, 보안(서버 IP 은닉), 정적 파일 서빙

## CDN

전 세계 여러지점(PoP)에 콘텐츠를 캐싱해두고, 사용자에게 가장 가까운 서버에서 콘텐츠를 제공하는 분산 네트워크이다.

**사용 이유**

1. 물리적으로 가까운 서버에서 응답 -> 지연시간감소
2. 정적 파일을 CDN에서 처리
3. 여러 엣지 서버가 있어 한 곳이 장애나도 서비스 유지
4. 대규모 공격 트래픽을 CDN이 흡수

## 웹소켓, HTTP 차이

**Websocket**

HTTP로 시작해 프로토콜을 업그레이드하는 양방향 실시간 통신 프로토콜이다.

**HTTP와의 차이**

- HTTP : 클라이언트 요청 -> 서버 응답 (단방향)
- WebSocket : 연결 후 서버도 능동적으로 데이터 전송 가능(양방향)

**SSE와 비교**

- Websocket -> 양방향. 채팅, 게임처럼 클라이언트도 자주 전송하는 경우
- SSE -> 서버 -> 클라이언트 단방향. 알림, 피드, 로그 스트리밍처럼 서버가 주도하는 경우, HTTP 기반이라 방화벽 친화적

## Rate Limiting

**Rate Limiting**

특정 시간 동안 사용자 또는 IP가 보낼 수 있는 요청 수를 제한하는 기법이다.

**필요한 이유**

- DDos
- API 남용 방지
- 서버 자원 보호 및 공정한 사용 보장
- 비용 제어

## gRPC

Google이 만든 고성능 RPC 프레임 워크이다. HTTP/2를 기반으로 Protocol Buffers로 데이터를 직렬화한다.
