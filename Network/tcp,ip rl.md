# TCP / IP 관련

## TCP/UDP의 차이점

- TCP는 연결형으로 신뢰성있는 데이터 전송을 보장한다. 
- 3-way-handshake로 연결하고, 패킷 손실 시 재전송, 순서를 보장한다.
- UDP는 비연결형으로 신뢰성은 적지만 오버헤드가 적어서 빠르다.

> 오버헤드 : 원래 목적 말고 추가로 드는 비용 
ex) 데이터 100만 보내면 되는데 헤더, 암호화, 변환, 검증땜에 실제로는 더 많은 시간/메모리/트래픽이 듬

TCP -> 정확성 중요, UDP -> 속도 중요

## TCP 3-way-handshake

연결 수립 (3-way-handshake)
1. 클라이언트가 서버에 연결 요청 패킷(SYN)을 보냄. 자신의 시퀀스 번호(ISN)를 포함한다.
> 시퀀스 번호 : TCP에서 데이터가 어떤 순서와 위치에 있는지 나타내는 번호. 순서 보장, 누락 확인, 재전송 제어에 사용.

2. 서버가 요청을 수락하고 자신의 SYN과 클라이언트 SYN에 대한 ACK를 보낸다.

3. 클라이언트가 서버의 SYN에 대한 ACK를 보내면 연결이 완료됩니다.

연결 종료 (4-way-handshake)
1. 클라이언트가 종료 요청 FIN을 보낸다.

2. 서버가 ACK를 보내고, 아직 보낼 데이터가 남아 있으면 계속 전송한다.

3. 서버가 모든 데이터 전송 완료 후 FIN을 보낸다. 

4. 클라이언트가 ACK를 보내고 TIME_WAIT 상태에 들어간다.

## TIME_WAIT, CLOSE_WAIT 상태

**TIME_WAIT**

연결을 먼저 끊은쪽이 마지막 ACK를 보낸 뒤 일정시간 대기하는 상태이다.

- 목적 : 지연된 패킷이 새로운 연결에 섞이는 것을 방지, 상대방이 FIN을 못받았을때 재전송
- 문제 : 클라이언트에서 TIME_WAIT 소켓이 과다하게 쌓이면 로컬 포트가 고갈될 수 있음

**CLOSE_WAIT**

클라이언트가 FIN을 보냈는데 서버가 FIN을 보지 않은 상태

- 문제 : 서버에 CLOSE_WAIT이 계속 쌓이면 애플리케이션이 소켓을 제때 닫지 않는 코드 버그를 의심해야함

## TCP의 흐름제어와 혼잡제어의 차이

**흐름 제어**

송신자가 수신자의 처리 속도를 초과하지 않도록 전송 속도를 조절한다.

**혼잡 제어**

네트워크 자체의 혼잡 상태를 감지해 전송 속도를 조절한다.

- 흐름 제어 -> 수신자 버퍼 보호
- 혼잡 제어 -> 네트워크 병복 방지

## 소켓

소켓은 네트워크 통신의 앤드포인트이다. 운영체제가 제공하는 통신용 API로, 애플리케이션이 네트워크 세부사항을 몰라도 통신할 수 있게 추상화한 것이다.

- 구성 : IP 주소 + 포트 번호

서버 소켓 흐름 : socket() -> bind() -> listen(), accept() -> read/write() -> close()

## TCP Keepalive

TCP Keepalive는 연결이 살아있는지 주기적으로 확인하는 메커니즘이다.

- 동작 : 일정 시간 동안 데이터가 없으면 빈 패킷을 보내고, 응답이 없으면 연결을 끊는다.

- 필요한 이유 
    - NAT 장비나 방화벽이 일정 시간 유휴 연결을 강제로 끊는 경우가 있음
    - 이미 끊어진 연결인지 모르고 소켓을 계속 들고 있으면 리소스 낭비

- 실무 활용 : DB 커넥션 풀에서 idle 상태로 오래 있던 커넥션이 중간 방화벽에 의해 끊겼는데, 애플리케이션은 살아있다고 착각하는 문제를 방지한다. HikariCP의 keepaliveTime옵션으로 해결
